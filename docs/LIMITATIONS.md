# Ограничения решения

Пункт 5 отчётного материала. Здесь то, что реально работает, то, что не
работает, и формулировки, которыми мы защищаемся. Числа — только измеренные;
источник каждой строки в `docs/TEST_RESULTS.md`.

## Поддерживаемые условия

- Android 9.0+ (minSdk 28; бриф допускает 26–28). Сборка под arm64-v8a,
  armeabi-v7a, x86_64.
- Вход: локальный файл (WAV / M4A / MP3 через SAF) **или** запись микрофоном
  приложения; всё сводится к 16 кГц моно.
- Выход: список реплик в UI + JSON брифа (`speaker_id`, `start_ms`,
  `end_ms`, `text`) в файл через SAF, либо «Поделиться».
- Офлайн-стенография работает в авиарежиме: модели лежат в APK
  (`assets/models`, ≈114 МиБ) и распаковываются в `filesDir` при первом
  запуске.
- PresentConnect — отдельный flavor с сетью, ≤20 потоков, optional.

## Заявка защиты = DEMO_STAGE6

Шесть русскоговорящих спикеров на сцене, **один** микрофон телефона, места
3–6 м, очередь реплик с лёгким перекрытием в конце, большая комната, средний
babble/HVAC, характер телефонного микрофона (band-limit, компрессия,
ослабление по расстоянию, реверберация). Это «идеальные» условия распознавания,
не студия.

| место | спикер | Hex WER baseline | после K≤6 + интонац. punct |
|---|---|---|---|
| 3.0 м | speaker_1 | 0.2857 | 0.2143 |
| 3.6 м | speaker_2 | 0.5833 | 0.3333 |
| 4.2 м | speaker_3 | 1.0000 | 1.0000 |
| 4.8 м | speaker_4 | 1.0000 | 0.9000 |
| 5.4 м | speaker_5 | 1.0000 (пропущен) | 1.0000 (не сопоставлен) |
| 6.0 м | speaker_6 | 1.0000 | 0.6923 |
| **aggregate** | — | **0.7794** | **0.6471** |

DER 0.2760, JER 0.5454, RTF 0.1173 (host Linux), спикеров в гипотезе **6 / 6**.

## Что честно не работает

- **Дальние места 4.2–5.4 м.** Реплики теряются или распознаются пустыми;
  speaker_5 не восстановлен. Усиление (`FarFieldGain`) и спектральный EQ
  (`PhoneDistanceEq`, 250–4500 Hz) **заморожены**: ни то ни другое не вернуло
  Hex WER 0.7794 на этом миксе, и дальнейшая подстройка чисел под фикстуру —
  это подгонка, а не решение.
- **Перекрытие речи** смазывает диаризацию; демо-запись делается с явной
  сменой реплик.
- **Один канал, один телефон.** Диаризация «коктейля» из 20 говорящих в
  комнате — измеренный провал (Path A: 1/20, DER 0.95), не заявка.
- **English — best-effort.** Zipformer-ru RU-first; для EN есть Whisper tiny
  как alternate модель, но не вторая полноценная цепочка.
- **Пунктуация.** Запятые ставятся по интонации/паузе, а не по школьным
  правилам (это и есть замоченное правило скоринга); на тексте Zipformer
  эвристические запятые срабатывают не везде — в замере speaker_1 остался
  только терминальный `.` плюс три удалённые запятые.
- **Скорость.** RTF 0.1173 — это host Linux (sherpa-onnx 2.0.1, x86_64).
  Он-девайс RTF на демо-телефоне ещё не замерялся.
- **Он-девайс проверка не выполнена.** `scripts/device-sideload-probe.sh`
  готов, но нужен живой телефон (Nothing-класс) — это human-действие.
- **Замер на последнем тибе не прогнан.** Строка K≤6 измерена на Impl
  `3c3f9ce`; тип `ab20d83` (не сливать s2/s3 под капом + карты тихих дальних
  мест) ещё не переоценён Eval.
- Долгое аудио без VAD-чанков деградирует; VAD обязателен.
- NNAPI у OEM плавает — провайдер по умолчанию CPU.

## Ограничения по итогам финальных прогонов (с источниками)

Каждая строка — из отчёта финишера или его артефактов; «REPORT agentN» =
`REPORT.md` соответствующей ветки.

**Устройства и верификация**

- Проверка — **только эмуляторы** (LDPlayer с ARM-трансляцией / официальный
  AVD x86_64). Прогон на физическом телефоне не выполнен:
  `android_device_execution: false` в
  `artifacts/optimization/verification.json` и
  `artifacts/compact/verification.json` (agent1); `scripts/device-sideload-probe.sh`
  остаётся human-действием на демо-устройстве (`apk/README.md` §Not yet done).
- **On-device мульти-спикерный транскрипт на эмуляторе не доказан до конца**
  (REPORT agent1, open issue №1): импорт → ASR → диаризация → LLM-пост-проход
  исполняются без краша/ANR, но LLM-фаза на эмуляторном x86_64 шла многие
  минуты и финальный JSON не был сохранён ни в одном прогоне (возможно,
  CPU-bound эмулятора, возможно, реальный hang — не диагностировано).
  Содержимое RU-распознавания подтверждено host-кросс-чеком тех же WAV.
- Эмуляторный e2e-фикстур (`stage6_sequential.wav`) — реконструированный
  чистый монтаж, а не замороженный room-микс: 4/6 реплик, фрагментация кропов;
  «not far-field proof» (agent1, `artifacts/compact/ldplayer-real-check.json`).
- Микрофон эмулятора пишет тишину: LIVE-поток доходит до `ГОТОВО`, но окна
  «речь не распознана» — живой микрофон возможен только на телефоне (REPORT
  agent1 §1.5; REPORT agent3, риск №7 — live-ASR проверен через файл/record).
  У agent2 изолированный AVD не запустился (WHPX-драйвер отсутствует),
  офлайн-sweep не перезапущен из-за adb-конфликта — офлайн-заявка опирается на
  аудит кода + успешный эмуляторный прогон (REPORT agent2).

**Диаризация и длинные записи**

- **Churn меток на живом микрофоне — исправлен в ship утром 2026-11-08**
  (hotfix-diar-mic: `f1b6abe` + casual-mic сцена `6ae5c39`, порог слияния
  голосов 0.45→**0.55**): демо-APK `5c9e9d76…` помечал каждую live-реплику
  отдельным спикером, потому что `FarFieldScene.stage6` форсировал K=6 на
  бытовых записях, а порог 0.45 лежал ниже измеренного медианного сходства
  того же голоса в шуме (0.51). Новая **casual-mic сцена** (офлайн/demo
  flavor) сохраняет VAD-recall stage6, но считает число спикеров
  **автоматически** (`expectedSpeakers=-1`, reconcile возвращает диаризацию
  как есть, near-field — без FarFieldGain-стейджинга). Провенанс: host-sweep
  `scripts/mic_diar_sweep.py` (sherpa-onnx 2.0.1 в `.venv`) + юнит-тесты
  (167 green); **замороженные строки DEMO_STAGE6 не переоценены** — они
  по-прежнему измеряются stage6-риг-харнесом (сцена с жёстким K=6,
  `scripts/host_asr_diar.py`), для casual/auto-count сцены отдельных
  eval-строк нет и числа по ней не заявляются.
- Исходные churn-наблюдения agent1 (до hotfix, остаются как история):
  DEMO_STAGE6 (3 ref-спикера) → 5 speaker ID, включая 202-мс
  сегмент с пустым текстом; `alternating_two_voices` (2 спикера) → первый
  блок `speaker_3`, остальное `speaker_9`; `E2E-2SPK_RU` (2 спикера) →
  сливается в один `speaker_1` (REPORT agent1, issue №2).
- Длинное аудио: 200-с `bench_long.wav` → pyannote «No speakers found in the
  audio samples», 0 сегментов (host) — **не исправлено** (REPORT agent1, issue №3).
- EN / code-switching непроверяемы: в checkout agent1 слот backup-ASR
  `models/asr/whisper-tiny/` пуст — фактически доступен только RU Zipformer
  (REPORT agent1, issue №4). **Демо-APK — RU-only.**

**Сборка**

- Инкрементальная упаковка APK недетерминирована (другой хеш/размер);
  clean-сборка воспроизводима побайтово (два независимых прогона, SHA256
  `5C9E9D76…7789`) — сдавать только clean-артефакты (REPORT agent1, issue №5).

**Локальная LLM**

- LLM-пост-проход — это **интонационная пунктуация на реплику**, а не
  саммари: ctx 1024, 2 потока, maxTokens 96; промпт саммари/ключевых решений
  в HEAD ветки agent2 нет (REPORT agent2). Саммари и Q&A по транскрипту
  добавляет ветка `agent3-product-features` (`llm/TranscriptLlm.kt`), качество
  ограничено моделью 0.5B (REPORT agent5).
- Qwen2-0.5B на длинных/EN входах часто выдаёт мусор (например, только
  `10000 мс.`). Транскрипт это испортить **не может**: `mergeCandidate`
  отклоняет кандидатов с изменёнными содержательными словами; цена — до
  ~2.2 с на реплику. Реплики длиннее 1664 знаков GGUF не получает —
  эвристическая пунктуация (REPORT agent2, `evidence.json`).
- **On-device GGUF-пунктуация медленная под ARM-трансляцией**: LLM-фаза
  ~330 с на 42-с фикстуре (LDPlayer SOV44, x86_64+Houdini,
  `artifacts/compact/ldplayer-real-check.json`); в smoke v1 43-с запись не
  прошла полный пайплайн за ~19 мин (`artifacts/SMOKE_PRESENTCONNECT.md`).
  На arm64-телефоне ожидается быстрее, но замер не выполнен.
- На ABI кроме arm64-v8a GGUF-движка нет (AAR arm64-only) — деградация до
  эвристики, UI это пишет.
- UI-мелочь не исправлена: строка `engineName = "llama.cpp GGUF …"`
  отображается и когда весов нет; честность держится красным fallback-текстом
  `llm-weights-missing (intonation punct only)` (REPORT agent2, баг №2).

**Экспорт**

- **Аудио-экспорта нет**: `MicRecorder` даёт только in-memory PCM;
  ре-энкода нет, импорт сохраняет исходный файл (REPORT agent2).
- **PDF с кириллицей**: валидный PDF-1.4 генерируется и открывается, но
  Helvetica не кодирует кириллицу — нужен встроенный шрифт; в репозитории
  шрифта нет, задокументировано, не исправлено (REPORT agent2, баг №4).

**Диаризация**

- Hard cap **6** спикеров — только в сцене DEMO_STAGE6 (`FarFieldScene`);
  casual-mic сцена офлайн-flavor'а (hotfix 2026-11-08) и flavor
  presentConnect используют auto-кластеризацию. Cap измерен на хосте
  (гипотеза 6/6), на физическом устройстве не подтверждён.

**Живая трансляция / сервер**

- **App→deck дым-тест 2026-11-08**: v1 — **FAIL** (hello отправлял `models`
  строкой, сервер ждал массив → `BAD_MESSAGE`, телефон не регистрировался);
  исправлено `f98bb03`, v2 re-smoke — handshake **PASS**
  (`phone_connected:true`), но строки транскрипта **из приложения** на дек
  не доставлены — **TIMEOUT** (0 строк за 8-мин бокс, тихий рестарт процесса
  на memory-tight эмуляторе). Живые 6 строк на деке доказаны curl-путём
  (agent3), не app-клиентом. Отчёты: `artifacts/SMOKE_PRESENTCONNECT.md`,
  `artifacts/SMOKE_PRESENTCONNECT_V2.md`.
- Демо-токены `09879078` (телефон и пульт) — **слабые по замыслу**: стенд
  публичный, секретов нет, но и защиты нет (REPORT agent4 §2; значения в
  `src/web/backend/src/config.ts` и в live-env).
- TLS — nginx + Let's Encrypt поверх **L4 SNI-роутера sslip.io**
  (`present.144.31.215.37.sslip.io`); fallback `https://144.31.215.37:8080` —
  самоподписанный сертификат, браузер ругается (REPORT agent3 §2).
- **Нет персистентности чекпоинтов**: перезапуск Node-процесса теряет сессию,
  транскрипт и слайд (in-memory only) (REPORT agent3, риск №1).
- **Нет стриминга токенов LLM**: `complete()` — блокирующий вызов,
  инкрементальных токенов на экране не будет (REPORT agent3, риск №2).
- **Нет метрик CPU/RAM**: HUD показывает `RAM — / CPU —`; числа не заявляем
  (REPORT agent3, риск №3).
- **45 с молчания телефона → fallback-баннер** «показана запись, не результат
  модели»; приложение должно пушить хотя бы раз в ~15 с (REPORT agent3, риск №4).
- Бэкенд **не имеет summary-эндпоинта** — экран саммари не обещаем (REPORT
  agent4 §1, by design).
- Сервер для команды **неизменяем** (SSH-ключи отозваны): если
  `neurosteno-web.service` упадёт, перезапустить его некому (REPORT agent4 §5).
- Свежий профиль Chrome на телефоне может показать First-Run/chooser до
  landing-страницы: достижимость URL 10/10, чистый UI-лендинг 6/10 под
  координатной автоматизацией; на сцене — пре-инициализированный Chrome
  (REPORT agent4 §1).
- QR-фикс (`4c5dd6e`, payload c `?session=…`) жив на сервере, но
  `github/main` его ещё не содержит — до любого редеплоя из репозитория нужен
  merge/cherry-pick, иначе фикс откатится (REPORT agent4 §5).
- Косметика: лейблы мест на живом слайде слегка наезжают друг на друга на
  узкой ширине (REPORT agent4 §1).
- Сборка agent3 делалась с `-x prepareEmbeddedModels`: свежая установка этого
  APK требует одного цикла распаковки моделей (REPORT agent3, риск №8).

**Продуктовый UI (ветка agent3-product-features)**

- Live-interim окно (5 с) — display-only плейсхолдер; финальный транскрипт
  всегда строится из полной записи (аудит целостности, REPORT agent5 §2).
  Косметика не исправлена: маппинг прогресса interim отстаёт от фактической
  фазы ASR; `liveInterim` не чистится из state (недостижимо в UI из-за гейта
  `running`).
- В `github/main` есть дублирующий коммит `4d1e0e4` (те же файлы экспорта/UI)
  — слияние конфликтует; интегратор должен выбрать одну сторону (REPORT
  agent5 §3).

## Формулировки на защите

Нельзя говорить:

- «WER_main = 0» как результат комнаты;
- «усиление/EQ вернули дальние места»;
- «Path B ≤20 — это наше демо»;
- «WORST_CASE / EDGE_* чистые WER/DER» (WORST_CASE: WER main 0.9130,
  DER 0.25ms-вариант 1.2985 — это FAIL);
- «жёсткий BAND_LIMITED на привязанных местах — это фикс» (он мягкий, ASR
  всё равно идёт);
- «диаризация дала 6 спикеров» без замера — было 12/6, стало 6/6 после
  хард-капа, и это измерено на хосте.

Можно говорить:

> Офлайн стенографист на одном телефоне: VAD → диаризация → Zipformer-ru →
> локальная LLM. Последний прогон Hex WER 0.6471 при DER 0.2760, гипотеза
> 6/6 спикеров; дальние места пока пустые. Пунктуация учитывается в скоринге,
> запятые по интонации, `ё`/`е` не наказывается. PresentConnect ≤20 —
> опциональный режим.

## Правила скоринга, которые мы зафиксировали

- Пунктуация входит в точность транскрипции (Mikhail Grigorev, Hex.Team,
  2026-11-06).
- Запятые следуют интонации говорящего, а не орфографии.
- `ё` ↔ `е` не учитывается. Нормализация: `scripts/eval_metrics.py`
  (keep-punct + fold), а не стандартный strip-punct WER из `eval/`.

## Что мы не делаем (п. 10 брифа)

- Аудио не уходит наружу: нет cloud ASR, cloud diarization, cloud LLM.
- Вычисления не выполняются на удалённом сервере. Хостовые прогоны
  (`artifacts/eval/`) — это **наши** замеры для отчётности, не путь обработки
  в приложении; в приложении весь пайплайн локальный.
- Нет подмены расшифровки заранее подготовленным текстом: `StubStenoPipeline`
  помечен в UI как stub и судьям не показывается; `IdentityLlmPostPass`
  остаётся тестовым дублёром, реальный путь — GGUF.
- Picovoice/Cheetah/Leopard (AccessKey) не используются; OEM
  `SpeechRecognizer` не является зависимостью.

## Лицензионные ограничения

- pyannote segmentation-3.0: веса MIT, но HF-репозиторий gated — мы берём
  копию из релизного тарбала sherpa и сохраняем атрибуцию (`NOTICE.md`).
- 3D-Speaker ERes2Net и Silero VAD: свои лицензии, редистрибуция через
  sherpa-onnx; атрибуция в `NOTICE.md`.
- Qwen2-0.5B-Instruct — Apache-2.0; llama-android — MIT; sherpa-onnx —
  Apache-2.0.
- Модели в git не кладём (`.gitignore`), APK и видео — тоже; сдаём как
  release-ассеты.

## Что не входит в версию

- Обучение/дообучение ASR, pyannote Python на телефоне.
- Word-level таймстемпы, переименование/слияние спикеров в UI, редактирование
  и перепрогон отдельного фрагмента (Ultra Pro Max из брифа).
- whisper.cpp как основной движок, облачный fallback.

## Риски демонстрации

- Забыть распаковать модели до авиарежима → stub на защите. Чеклист и
  распознавание состояния — в UI (`pipeline = stub`, `LLM: …`).
- 353 МиБ GGUF внутри APK: если собираем `-PembedLlm=true`, артефакт
  становится ~530 МиБ — скачивать заранее и по Wi-Fi.
- На armeabi-v8a-32/x86_64 GGUF-движок отсутствует (AAR только arm64) →
  LLM-пост-проход деградирует до интонационной эвристики, UI это пишет.
